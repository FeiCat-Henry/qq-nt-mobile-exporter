# 原理与数据结构

面向想改代码 / 换版本后重新适配的人。数据来自一台 Android 15、arm64-v8a、QQ 2025-09 版的真机。

## 1. 库在哪里

```
/data/data/com.tencent.mobileqq/databases/nt_db/nt_qq_<32位hash>/     ← 每个登录过的账号一个目录
├── nt_msg.db            121 MB   消息主体(最重要)
├── profile_info.db      11.5 MB  好友资料/昵称
├── group_info.db        10.3 MB  群资料/群成员
├── buddy_msg_fts.db     37.7 MB  好友消息全文索引(可选)
├── group_msg_fts.db     13.0 MB  群消息全文索引(可选)
├── guild_msg.db         56.4 MB  频道
├── files_in_chat.db     12.2 MB  聊天文件索引
└── misc.db / emoji.db / ...
```

多账号会有多个 `nt_qq_<hash>` 目录，`send` 前建议先确认哪个是当前主号（体积最大的那个）。

## 2. 加密格式

- 标准 NTQQ SQLCipher：1024 字节页、4 KB 页大小、16 字节 salt，正常解出来就是普通 SQLite。
- **但手机版多一层 1024 字节扩展头**，由 `nt_sqlite3_init_extheader / read_extheader / write_extheader` 处理。表现就是：拿到正确 key 自己 `open_v2 + key`，仍然返回 `rc=26 file is not a database`。
- hook 到的 key 是 **32 字节 ASCII 字符串**（日志里会打成 `len=32 hex=<64 位十六进制>`，解出来是一串可打印字符），不是 16 字节二进制。`PRAGMA key="x'...'"`（二进制）路径**不适用于**它。

结论：别想着拿 key 离线解，直接借 QQ 的连接执行 `sqlcipher_export()` 最稳。

## 3. hook 用到的符号

都在 `libbasic_share.so`（约 6 MB），是**正常导出**的符号（`enumerateExports` 能看到 266 个 `nt_sqlite3_*`）：

| 符号 | 典型偏移(本版本) | 用来干什么 |
|---|---|---|
| `nt_sqlite3_open` | `0x513188` | 记 句柄→路径 |
| `nt_sqlite3_open_v2` | `0x513618` | 同上 |
| `nt_sqlite3_key` | `0x4f8cfc` | 记 key + 触发导出 |
| `nt_sqlite3_key_v2` | `0x4f8d30` | len 在 args[3]、key 在 args[2] |
| `nt_sqlite3_exec` | `0x50fe74` | 执行导出 SQL / `PRAGMA database_list` 探路 |
| `nt_sqlite3_prepare_v2` | `0x52650c` | 兜底触发 |
| `nt_sqlite3_init_extheader` | `0x51ef84` | 扩展头(自己开库必踩) |
| `nt_sqlite3_read_extheader` | `0x51f2b8` | 同上 |
| `nt_sqlite3_write_extheader` | `0x51f3a0` | 同上 |

> 偏移只是本版本参考，**不要硬编码**。脚本一律按名字 `findExportByName` 取。

`libkernel.so`（41 MB）里那份 SQLCipher 符号被剥掉了，`.dynstr` 里连 `PRAGMA journal_mode;`、`sqlcipher_export` 这些字符串都没有（是 DLL 占位），按符号或字符串都定位不到。

## 4. 句柄 → 路径反查

attach 时库很可能早就打开了，`open` 的 hook 错过了。可靠办法是问 SQLite 自己：

```sql
PRAGMA database_list;
-- 0=seq 1=name 2=file
```

用 `NativeCallback` 接住结果，取第 3 列就是文件路径，从而把 `db handle` 关联回库名。

## 5. `nt_msg.db` 关键表

```
c2c_msg_table      好友消息    138,425 行(本机)
group_msg_table    群消息       15,276 行
c2c_msg_flow_table / discuss_msg_table / draft_storage_table_v1 / ...
```

`c2c_msg_table` 的列是数字命名的（保留字段号），实际有意义的几个：

| 列 | 含义 |
|---|---|
| `40001` | 消息 id（**int**，不是文本） |
| `40013` | 发送者/自己 标记（判断「我 / TA」） |
| `40020` | 发送者 uid（`u_xxxx`） |
| `40021` | 会话对端：好友 uid 或群号 |
| `40033` | 发送者 QQ 号 |
| `40050` | 时间戳（秒） |
| `40800` | **消息体 blob**（正文在这里） |

## 6. `40800` 的消息体结构

外层是 protobuf，字段号也是"业务号"：

```
40800 (len)                   ← 一条消息
  ├ 45001 (varint) 段 id
  ├ 40020 (string) 发送者
  ├ 45002 (varint) 内容类型  1=文本 2=图片 3=文件 4=视频 6=表情 7=回复 8=语音
  ├ 45101 (len)    ← 正文/媒体信息
  └ 45102 (varint)
```

**电脑版与手机版在 `45101` 上不同**：

- 电脑版：`45101` 里是一段**嵌套**结构，正文藏在更里层，需要按 protobuf 递归取。
- 手机版：`45101` 里就是**原始 UTF-8 字节**。

实测一条文本消息的原始字节：

```
82 f6 13 3f                                  40800, len=63
  c8 fc 15 b6 f5 fc e2 f2 bc e0 c2 65        45001 = 段 id
  d0 fc 15 01                                45002 = 1 (文本)
  ea 82 16 27                                45101, len=39
     e5 a5 bd e5 a5 bd e5 a5 bd ef bc 8c ...  ← 正文 UTF-8:「好好好，实力哥...」
  f0 82 16 00                                45102
```

所以 `mobile_text()` 的判断是：**`45002 == 1` 的段，其 `45101` payload 若能整体按 UTF-8 解码且不含控制字符，就当正文**。这个条件同时把电脑版的嵌套结构排除掉了（那串二进制解 UTF-8 会带控制字符）。

群消息的文本段常常嵌在 `ctype=7`（回复）里，所以 `mobile_text` 对外层段做**递归**再取。

## 7. `group_info.db` 群成员

```
group_member3   34,026 行
 64003  群内名片(可能为空)
 20002  昵称
 60001  群号
 1000   uid (u_xxx)
 1002   QQ 号
```

群名在 `group_detail_info_ver1."60007"` / `group_list."60007"`（key 都是 `60001`=群号）。

只包含**当前仍在群里**的成员 —— 这就是历史消息里退群成员显示「成员」的原因。

## 8. 为什么可以不要 FTS 库

`buddy_msg_fts.db` / `group_msg_fts.db` 只是全文检索索引，且 QQ 只在真正做搜索时才打开它们。正文本来就在 `nt_msg.db."40800"` 里，所以：

- 导出完全不需要 FTS 库；
- 抓不到它们时，导出器不再报错（`export_items` 里已改成可选）。

## 9. 被证伪的几条路（别再试）

1. **`MsgBackup/` 备份包离线解**：4 个大库前 115 字节完全一致（伪 `SQLite format 3` + 声明 1024 页 + `MSG0`，自相矛盾），正文熵 7.01–7.02，8 MB 内没有任何 `CREATE TABLE`/`sqlite_master` 明文，不是压缩格式。私有容器，不可行。
2. **旧版明文库 `<QQ号>.db` 反推 IMEI 密钥**：字段层是逐字节 XOR 密文（`Friends.uin`=`\x01\x05\x07\x04...`），对 417 条样本做长度 2–24 的循环密钥约束求解，**没有任何长度能同时满足**。
3. **拿 key 自己开库导出**：`rc=26`，见第 2 节。
4. **`libkernel.so` 里按符号/字符串找 sqlite**：符号剥没了，字符串也没有。
